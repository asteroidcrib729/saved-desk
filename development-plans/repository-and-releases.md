## Reproducible build inputs

The verified local environment uses Windows x64, Node 24.21.0, Python 3.14.7, Rust 1.99.0 (MSVC), Visual Studio C++ desktop tools/Windows SDK and WebView2. A fresh Windows checkout requires those build tools. Version-pinned dependencies reduce drift; this is not a claim of bit-identical executables, reproducible timestamps or a complete SBOM.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r packaging/requirements-lock.txt
.\.venv\Scripts\python.exe -m pip install --no-build-isolation -e backend

.\.venv\Scripts\python.exe packaging/audit-repository.py
powershell.exe -NoProfile -ExecutionPolicy Bypass -File packaging/build-release.ps1 -Tag v0.2.10
```

Use a fresh checkout for releases so old copied resources cannot enter a new package. The build creates the static frontend, worker, bundled Node runtime, offline WebView2 prerequisite, browser connector, native host and per-user x64 NSIS installer. The release collector requires a newly produced installer and refuses to overwrite an existing local asset directory. Use `-CollectExisting` only to collect an installer already built and verified (for example after external signing); it does not rebuild or establish freshness, and the manifest records that choice. The GitHub workflow always uses the fresh-build default. Output under ignored `release-artifacts/v0.2.10/` includes setup EXE, connector ZIP, SHA-256 checksums, source-commit/build metadata, review notes and tool-license inventory. The collector now includes original source, verbatim notices and recorded dependency source archives; `acceptance-review.json` records actual payload source/notice, host installer, signing and live-platform gates separately. Collected 0.2.10 assets pass payload and host gates; signing and fresh live-platform gates remain false.

All desktop, npm lock, Rust package/lock, Tauri Python worker package and `social_downloader.__version__` versions must agree. Connector version derives from the desktop package. ## GitHub release workflow

`.github/workflows/ci.yml` checks source/ignore rules, Python, connector, TypeScript, static export and UI on Windows. `.github/workflows/release-windows.yml` is manually dispatched for an existing version tag; it repeats those checks, pins Rust, runs native unit checks, builds a fresh installer and uploads review assets. Actions are pinned to verified official commits. Build jobs have read-only repository permissions, checkout credentials are not persisted, and only the optional draft job receives write permission. GitHub-hosted execution remains unverified until this source is pushed.

After source checks pass, create and push the matching tag:

```powershell
git tag -a v0.2.10 -m "SavedDesk 0.2.10 review"
git push origin v0.2.10
```

On GitHub, open **Actions -> Windows release preview -> Run workflow**, enter the existing tag, and leave **Create a private draft prerelease** off to build review artifacts only. Enable it when you want a draft created for review. It uses the tag's source, verifies its versions, never overwrites an existing release and never publishes automatically. Download review artifacts from the workflow run. If a draft was requested, review its assets and notes under **Releases**, complete the gates below, then publish deliberately.

GitHub Releases attach installer assets to a version/tag while retaining source archives. See [GitHub releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases) and [managing release drafts](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository). NSIS delivery and WebView2 bootstrap behavior are described in [Tauri's Windows installer guide](https://v2.tauri.app/distribute/windows-installer/).
